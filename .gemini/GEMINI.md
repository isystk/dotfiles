# Global Gemini Settings

このファイルは全プロジェクトに適用されるグローバル設定です。
言語固有のルールは各リポジトリの `.agent/rules/` ディレクトリに配置します。

## Language

常に日本語で応答してください。技術用語やコード識別子は原文のままで構いません。

## Communication Style

### 質問は1つずつ

質問が必要な場合は、一度に複数の質問をせず、1つずつ確認してください。

### 簡潔な応答

- 冗長な説明を避け、要点を簡潔に伝える
- コード例は必要最小限に
- 絵文字は使用しない（明示的に要求された場合を除く）
- 作業完了後の長文サマリーは避け、変更点を簡潔に報告する

## Editing Policy

- 依頼された範囲外のコード・ファイルは変更しない
- 既存ファイルへの編集を優先し、新規ファイル・ドキュメント（README等）は必要な場合のみ作成する

## Assumptions

- 存在しないAPI・ライブラリ・設定を仮定しない
- 広範囲の変更、DBスキーマ変更、API仕様変更、ディレクトリ構成の変更は事前に確認する

## Working Style

### コード変更

- 変更は必要最小限に留める
- 過剰な抽象化やリファクタリングを避ける
- 将来の要件を先取りした実装をしない

## Serena MCP の活用 (Core Workflow)

`serena` スキルを最優先で活用し、「プロジェクト文脈の保持（Memory）」と「高速な実行」を両立させてください。

### 開発原則

- **TypeScript First**: すべてのコードは TypeScript で記述し、厳密な型定義を行う。
- **No Comments**: ソースコード内の説明コメントは不要。ロジックが極めて複雑な場合に限り、可読性維持のための最小限のコメントを許容する。
- **Best Practices**: SOLID原則、クリーンアーキテクチャ、業界標準のパターンをデフォルトで適用する。
- **Security**: JWT、認証ミドルウェア、厳密な入力バリデーション（Zod/Pydantic等）を必須とする。

## Memory System: 階層型ナレッジベース

`.serena/memories/` は **追記専用のログではなく、キュレーション型のナレッジベース** です。本番コードと同じ感覚で扱い、増やすのと同じ頻度で減らしてください。各エントリには「ロード時間・ノイズ・矛盾するアドバイス」というコストがあるため、存在価値を常に問い直します。

### Tier 1 — Hot Memory（毎タスクでロード）

以下6ファイルはタスク開始時に必ず読み込みます。**情報密度が高く、無駄のない状態を維持** してください。

| ファイル | 範囲 |
|---|---|
| `project_overview.md` | スタック、ディレクトリ構成、アーキテクチャ決定 |
| `conventions.md` | コーディング規約、ワークフロー、コマンド |
| `pitfalls.md` | 落とし穴、エラー → 修正レシピ |
| `patterns_backend.md` | 再利用可能なバックエンドパターン (PHP/Laravel/Python 等) |
| `patterns_frontend.md` | 再利用可能なフロントエンドパターン (React/TS) |
| `testing_guide.md` | テストレシピ、Mockery/Vitest 等のTips |

### Tier 2 — Archive（関連時のみロード）

`archive/issue-{id}_{slug}.md` — 一次実装記録。タイトルだけスキャンし、現タスクと同じ領域の場合のみロード。

## Quality Gate（メモリ書き込み**前**に必ず実行）

以下の4問を順に確認。**最初に「No」が出た時点で破棄** してください。

1. **再利用性があるか？** — このタスクと違う、未来のタスクでも役に立つか？（1行スクリプト備忘録、diff の再掲、一発の設定スニペットは NO）
2. **コードから自明でないか？** — 未来の AI がコードベースを 30秒読めば再導出できる内容か？（メソッドシグネチャ、明らかなファイル位置 → NO。微妙な TZ バグの修正、非自明な API のクセ → YES）
3. **配置先が決まっているか？** — パターン → `patterns_*` / 落とし穴 → `pitfalls` / 規約 → `conventions` / 構造決定 → `project_overview` / テストレシピ → `testing_guide` / 一次記録 → `archive/`。**配置先が決まらない情報は、たいていメモリ保存に値しません。**
4. **既存と重複していないか？** — 既存メモリを検索。類似内容があれば、**新規ファイルを作らず既存エントリを編集（統合・追記）**。

### Anti-Patterns（**絶対に保存しない**）

- 「スクリプト X がパス Y にある」だけの存在通知（非自明なレシピが付かないもの）
- diff やコミットメッセージを再掲しただけの手順書
- 冗長なトラブルシュート履歴 — **最終的な根本原因 + 修正だけ** 残す
- 推測、WIP メモ、「いずれ〜したい」系の願望
- コードのコメント・型に既に書かれている情報
- PR 単位の変更ログ（それは git の役割）

## Memory Lifecycle

### Phase A — Read（タスク開始時）

1. Tier 1 ファイルを **すべて** `serena` でロード。
2. `archive/` のタイトル一覧をスキャン。直接関連するエントリのみ追加ロード。

### Phase B — Implement（実装）

コードファースト。メモリ書き込みは Phase C/D に遅延させる。

### Phase C — Retain（タスク完了時：追加）

タスク中に得た知見ごとに：

1. 上記 **Quality Gate** を適用。
2. 正しいファイルに振り分ける（Tier 1 の表を参照）。
3. **append より merge**: 関連エントリが既にあれば、新セクションを増やさず既存を編集（統合・箇条書き追加・文言改善）。
4. エントリは高密度に：1原則=1箇条、コードスニペットは「原則だけでは伝わらない場合」に限定。

### Phase D — Prune（タスク完了時:削減 — **必須、省略不可**）

Tier 1 ファイルに何らかの書き込みを行ったら **即座に**：

1. 修正したファイルを最初から最後まで再読。
2. 新規エントリだけでなく、**既存エントリ全部に対して** 下記の Pruning Heuristics を適用。
3. 削除・統合・昇格・降格を実施。
4. `archive/` が膨らんでいたらスキャン：再利用可能な知見は `patterns_*` / `pitfalls` へ昇格、純粋な歴史的ノイズは削除。

**Phase D を実行していないタスクは未完了** とみなします。

### Pruning Heuristics（迷ったらこの基準で）

| シグナル | アクション |
|---|---|
| 「既に現在のコードに反映済みで、再導出が容易」 | **削除** |
| 「別エントリと根本原因が同じ、症状が違うだけ」 | **統合**（1エントリに発生箇所をすべて列挙） |
| 「過去の diff を語っているだけの手順」 | **削除**、原則・ヒューリスティクスのみ残す |
| 「削除済み機能、廃止ライブラリ、古いファイルパスを参照」 | **削除** |
| 「一次実装記録だが汎用パターンに昇華できる」 | `archive/` → `patterns_*` (または `pitfalls`) へ **昇格** |
| 「Tier 1 にあるが特定issueでしか発火しない」 | `archive/` へ **降格**（または価値が低ければ削除） |
| 「同じライブラリ/領域の説明が1ファイル内に3つ以上ある」 | **統合**：1見出しの下にまとめる |
| 「エントリが書かれて以降、参照されておらず、関連コードも変化した」 | **削除**（サンセット） |

### Sizing Guardrails（ソフトリミット、超えたら整理）

- `pitfalls.md` がセクション 15個 超 → 領域ごとに統合
- `patterns_*.md` が 12 パターン超 → サブドメイン分割 or 類似統合
- `archive/` が 10ファイル超 → 監査。**ほとんど削除可能なはず**
- 単一 Tier 1 ファイルが 400 行超 → 再構造化

## Execution Workflow

### 1. Context Load
- Tier 1 メモリ全件
- 必要に応じて Tier 2 を選択ロード

### 2. Implement
- TypeScript ファースト、コメント排除、セキュリティ優先

### 3. Retain & Prune
- Phase C（追加）: Quality Gate → ルーティング → append より merge
- Phase D（削減）: 修正ファイル再読 → Pruning Heuristics 適用 → 削除/統合/昇格/降格

**次のタスクを高速化しない知識はノイズです。** 加算と同じ頻度で減算してナレッジベースを育ててください。

## Project-Specific Settings

プロジェクト固有の設定は各プロジェクトの以下に配置：

- `GEMINI.md` - プロジェクト共通設定（Git管理）
- `.agent/rules/*.md` - プロジェクト固有ルール（Git管理）
