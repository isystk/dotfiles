# Security Rules

## General

- セキュリティを利便性より優先する
- 不明な場合は安全な実装を選択する
- セキュリティリスクがある変更はユーザーへ確認する

## Secrets

- APIキー・アクセストークン・パスワード・秘密鍵をソースコードへ記述しない
- 機密情報は環境変数またはシークレット管理サービスから取得する
- 機密情報をログへ出力しない
- サンプルコードにはダミー値を使用する

## Authentication & Authorization

- 認証・認可をバイパスしない
- 権限チェックを省略しない
- 最小権限の原則を守る
- リクエストで受け取ったID(URL・ボディ・参照先)で資源を取得するときは、所有者と権限を必ず検証する(IDORを作らない)
- ログイン・パスワード再設定の応答から、アカウントの存在有無が分かる差異を出さない(ユーザー列挙)
- ログイン時にセッションIDを再生成し、パスワード変更・再設定後は既存セッションを失効させる

## Rate Limiting & Abuse Prevention

- 認証系と公開APIには回数制限を付ける
- キーは「アカウント+IP」と「IP」の二段にする。単一の識別子(メールのみ等)だけで上限を設け、第三者が他人を締め出せる状態にしない
- 未認証はIP、認証済みはユーザーで数える
- 信頼するプロキシを設定し、CDN/プロキシのIPではなく実クライアントIPで判定する(未設定だと全員が同一IP扱いになり誤って429になる)
- 外部サービスを叩く処理は、サーバー共有IPで相手側の制限を消費しないよう自前の上限を設ける
- エッジ(CDN/WAF)の制限と役割を分ける。エッジは短時間の連打、アプリは分単位の総当たりを止める

## Input Validation

- 外部入力は必ず検証する
- 入力値を信用しない
- SQL・HTML・シェルコマンドへ入力を直接埋め込まない
- 入力値で件数・期間・外部API呼び出しが増えるエンドポイントは、上限を設け、外部APIを叩く入力は許可リスト(enum)で検証する(増幅攻撃。回数制限だけに頼らない)

## Database

- パラメータ化クエリまたはORMを利用する
- SQL Injectionの原因となる実装を行わない

## Output

- 出力時に適切なエスケープを行う
- XSSの原因となるHTML出力を行わない

## File Handling

- パストラバーサルを防止する
- アップロードファイルはサイズ・拡張子・MIMEタイプを検証する
- ユーザー入力からファイルパスを組み立てない

## External APIs

- HTTPSを使用する
- タイムアウトを設定する
- 必要に応じてリトライを実装する
- 外部レスポンスを信用しない

## Logging

- 個人情報や機密情報をログへ出力しない
- ログには必要最小限の情報のみ出力する

## Dependencies

- 信頼できるライブラリを利用する
- 不要な依存関係を追加しない
- 脆弱性が報告されているライブラリの利用を避ける

## Git

- `.env`
- APIキー
- 秘密鍵
- 証明書

はコミットしない

## Safety

- セキュリティ機能を無効化して問題を回避しない
- 開発用の設定を本番環境へ持ち込まない
- セキュリティ設定・ルートを変更したら、本番では設定/ルートキャッシュを再生成し、常駐ワーカー(キュー等)を再起動する。忘れると新しい制限が効かない
- 本番に攻撃的なリクエストを送らない。回数制限や認可の再現はローカル・テストで行う
