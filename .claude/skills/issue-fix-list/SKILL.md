# Issue Fix List Skill

## Goal

調査・検討の結果を、チケットや報告にそのまま貼れる「要件・課題と対応案」のリストにする。
要件・課題と対応案を1対1で並べ、読み手が上から順に追うだけで、何が課題で何をするかが分かる状態にする。

## 1. 書式（固定）

```
要件・課題と対応案

1. {要件・課題の要点を短く（現象を名詞句や短文で）}
   - 要件・課題: {事実と原因。数値や条件があれば添える}
   - 対応案: {何をどうするか}
2. …

対象外・残課題
- {今回やらないこと、未確認のこと、確定していないこと}
```

- 見出しは「要件・課題と対応案」と「対象外・残課題」の2つ。
- 項目は番号付き。各項目は「要件・課題:」「対応案:」の2行を基本にする。
- 検討観点への回答（例: ライブラリを載せ替えるか）は、最後の項目にして、「要件・課題:」「対応案:」の代わりに「結論:」「確認結果:」を使ってよい。
- 項目の数は、重要なものに絞る（目安は4〜6）。細かいものは元の文書に任せる。

## 2. 書き方のルール

- 元になる文書（方針書・調査結果・チケット）を先に読み、内容を写す。新しい主張は足さない。
- 1項目に、要件・課題は1つ、対応案は1つ。複数の要件・課題を1項目に混ぜない。
- 事実と推測を分ける。未確認のことは「推測」「原因は推測」「未確認」「未実施」と明記する。
- 数値は根拠のあるものだけ。目安は「約」を付ける。
- 1文は短く。専門用語には補足を付ける。
- 対応案は、実際に決めた内容を書く。まだ決まっていないことは、対応案に書かず、残課題へ回す。
- 確認できたこと（テスト結果など）は、「確認結果:」か、対応案の末尾に短く添える。確認していないことは「確認できた」と書かない。

## 3. 作り方

1. 元の文書を読み、要件・課題を洗い出す。
2. 要件・課題ごとに対応案を対応させる。対応案のない要件・課題は、残課題へ回す。
3. 上の書式で、チャットに出力する（ファイルにするのは、依頼されたときだけ）。
4. 出力後に、事実と推測の区別、数値の根拠、未確認の明記を点検する。

## 4. 関連

- 画像にする場合は、`issue-fix-infographic` スキルを使う。対応は次のとおり。
  - 番号付きの1項目 → 画像の「要件・課題 → 対応案」の1行
  - 「結論:」「確認結果:」の項目 → 画像の「確認できたこと」欄
  - 「対象外・残課題」 → 画像の同名欄
