# ログ検知ルール(攻撃の兆候)

アクセスログを定期集計して兆候を検知する。**検知と通知に限定**し、遮断はエッジのレート制限に任せる(定期実行では自動遮断に遅い)。

## 1. シグナル一覧

| # | シグナル | 見方 | 誤検知の主因 |
|---|---|---|---|
| S1 | 既知の攻撃ツールの UA | UA 文字列の一致 | ほぼ無し(UA 変更で無効化される) |
| S2 | 既知 SDK 由来の UA(先頭一致) | 同上 | 同 SDK を使う他ツール |
| S3 | 同一 IP の 404/400 が短時間に多発 | 件数のしきい値(例: 10 分に 40 件) | リンク切れ、自分のスキャン、監視ボット |
| S4 | 同一 IP の参照 URI の種類が多い(列挙) | ユニーク URI 数(例: 60 種) | クローラ、RSS リーダー |
| S5 | 注入・トラバーサル様のクエリ | `../`、`' or `、`union select`、`<script` など | 正当な入力、セキュリティ製品の検証 |
| S6 | 認証系パスへの集中、401/403 の継続 | 件数 + 継続 | 通常のログイン失敗、IP 制限による正当な 403 |
| S7 | S3・S5・S6 が同一 IP で短時間に揃う(相関) | 3 つの AND | 許可済みの診断(除外リストで対応) |
| S8 | 深夜帯の継続的高頻度アクセス | 時間帯 + 件数 | 海外の正規利用者、定期ジョブ |
| S9 | CDN を経由しないオリジン直撃 | 観測ログの `from_cf=0` | グレー雲ホスト、サーバー自身からの呼び出し |

しきい値は初期案。**1 週間のベースラインを見て調整**する。

## 2. 設計の要点

- 入力: リバースプロキシのアクセスログ。実クライアント IP が取れているか(`real_ip` 設定)を先に確認する。取れていないホストでは、ログの IP が CDN のエッジになり、IP 単位の集計が成立しない(→ `CF-Connecting-IP` 等を記録する形式に拡張)
- 判定キー: 直撃(S9)は、偽装できるヘッダ(`CF-Connecting-IP`)ではなく**接続元アドレス**(`peer`)で判定する
- 除外リスト: 自分の IP、サーバー自身の公開 IP(自分のスキャンや自動投稿が出る)、CDN のレンジ、既知の監視ボット。設定ファイルに分離し、CIDR で書けるようにする
- 状態管理: 「IP + ルール」単位の最終検知時刻を保存し、一定時間(例: 24 時間)は再通知しない
- 実行: 10 分間隔の別 cron(`flock` で多重起動を防ぐ)。日次ジョブはサマリー集計のみ
- 解析不能な行: 無視せず件数を出す(`解析不能 n 行`)。形式違いの行(別ログ、400 の不完全な行)が S3 を取りこぼす原因になる

## 3. 通知の絞り込み

背景スキャンは常に鳴る。通知を全ルールに出すと、本当の兆候が埋もれる。

- 通知: 多段相関(S7)、既知ツールの UA(S1/S2)、直撃(S9)、ログ異常(ログが無い・形式が変わった)
- 通知しない: 単発のしきい値超え(S3〜S6)。日次サマリーに `[集計] S3=n S4=n S5=n S6=n`(規則別の検知 IP 数)として出す
- **S3 に 403 を含めるか**: 既定は含めない。エッジで遮断済みの通信を数えると、背景スキャンで件数が膨らみ、変化が見えなくなる。ただし 403 しか返さないホスト(IP 制限)を叩き続ける多段攻撃は S3 が立たない。必要になったらオプションで有効化できるようにしておく
- S9 の重大度: 強制前(②まで)は WARN、強制後(③)は ALERT。直撃が応答(status<400)を得た場合に重くする

## 4. 導入手順(誤通知で信頼を失わない)

1. **記録のみ**で cron 登録(通知フラグなし)。数日、ログに結果を残す
2. dry-run で、誤検知(自分の IP、定期ジョブ、CDN のヘルスチェック)がないか確認し、除外リストを整える
3. baseline: 現在の検知を全て「通知済み」として状態に入れる(通知は送らない)。有効化直後に過去分が一斉に鳴るのを防ぐ
4. 通知フラグを追加して有効化
5. 解析不能な行の件数が多ければ、形式を調べてパターンを足す

ロールバック: cron を外すだけ。状態ファイルとログは残してよい。

## 5. 検知後の一次対応(侵害が疑われる場合)

検知は「疑い」であり、停止・公開停止の判断は利用者と行う。**証拠保全 → 遮断 → 立て直し**の順を守る(先に消すと原因が追えず、遮断を緩めると再侵入される)。

1. 影響範囲を確定する: 対象ホスト、時間帯、送信元 IP、`status<400` を返したリクエストの有無
2. 遮断を一時強化する: エッジの WAF で該当 IP/CIDR と該当パスを拒否。オリジンは IP 制限で絞る
3. 証拠を保全する: アクセスログ・アプリログ・pcap を別ホストへコピー(圧縮してから。上書き・ローテーションで消える)。対象ホストの設定ファイル、`docker ps -a`、`crontab -l`、`last`、`ss -tunap` も控える
4. 認証情報をローテーションする: API トークン、DB・メールのパスワード、SSH 鍵、セッション署名鍵。**漏洩の可能性がある順に**
   - 注意: アプリの `APP_KEY` 相当を変えると、暗号化済みの認証情報が復号不能になる(実例あり)。先に再暗号化の手順を用意するか、該当データの再登録を前提にする
5. 侵害前提で立て直す: コンテナイメージの再ビルド、不要な公開ポートの閉鎖、`/tmp` など実行可能ディレクトリの確認、追加された鍵・root CA の削除
6. 復旧を確認する: 通常応答、`cf-cache-status: DYNAMIC`、定期ジョブの成功、新規の異常ログが無いこと
7. 記録する: 時系列・判断・実施者。点検書(`references/app-authz-checklist.md` のテンプレート)に残す

## 6. ホスト側チェック(補完)

ログ検知で見えないものは、ホスト側の定期チェックで補う。

- 想定外のコンテナ、想定外の待受ポート
- 追加された root CA、開発用プロキシの痕跡
- ファイル整合性、ログイン試行
