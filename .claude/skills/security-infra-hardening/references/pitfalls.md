# よくある罠(インフラ側)

## ログ・IP

- **`real_ip` が無いホストでは、ログのクライアント IP が CDN のエッジ IP になる**。IP 単位の検知や除外が効かない。CDN が付けるヘッダ(`CF-Connecting-IP`)を別途ログに出す。CDN 経由かどうかの列(`from_cf`)だけが CDN 経由/直撃を区別できる
- サーバー自身の公開 IP から、自分の定期ジョブ(自動投稿・スキャン・wp-cron)が CDN 経由で届く。検知の誤検知源になるので除外リストに入れる。また、AOP を強制しても遮断されない通信(CDN 経由で届くため)である点に注意

## nginx / 設定ファイル

- `log_format` や `geo` は、使う側(`access_log`)より**先に読まれる場所**に置く。後ろだと `nginx -t` が未定義エラーで失敗する
- 切り戻しは「使う側(`access_log`)を先に削除 → 定義側(`log_format`/`geo`)を削除」の順
- `access_log` の出力先ディレクトリを**消す前に**、`access_log` の行を消す。逆だと、管理ツールで保存したホストが `.err` 化してオフラインになる
- 共通 include(全ホスト共通)に書いた内容は、**グレー雲のホストにも効く**。遮断系の設定を共通 include に書かない
- reload の前に必ず `nginx -t`。失敗したら reload しない(旧設定のまま動き続ける)

## GUI 型リバースプロキシ(Nginx Proxy Manager など)

- 画面で保存すると、内部で `nginx -t` が走り、失敗するとそのホストの設定が `.err` になり**オフライン**になる。CA のパス誤りなど1つのミスでホストが止まる。1 ホストずつ保存し、Online と `.err` 無しを確認する
- カスタム設定(`advanced_config` 等)の DB 上の型に注意(TEXT/BLOB)。スクリプトで書き換えるときは型を確認する。BLOB 型だと保存時に文字列として扱われず `.err` 化する経路がある
- 画面が開けなくなったときの復旧手段(DB と生成済み設定の両方を直す手順)を、変更前に確認しておく
- コンテナを作り直すと、`:latest` タグの版が変わり、意図しない変更が入る。設定変更では再作成せず reload で反映する

## CDN

- **Cache Rule・WAF ルールの式にホスト名が無い → ゾーン内の全サブドメインに効く**。復旧は、ルール無効化 + キャッシュの全パージ(無効化だけでは最大 TTL 分、キャッシュが残る)
- AOP の Global トグルは**ゾーン内の全オレンジ雲**に効く。グレー雲のホストは対象外
- 変更後は、同じゾーンの他ホストの `cf-cache-status` が DYNAMIC のままか確認する

## サーバー内通信

- IP 制限・AOP は、**同一サーバー内のサービスが公開 URL 経由で他ホストを呼ぶ通信**を巻き込む(nginx から見た送信元はサーバー自身の公開 IP)。導入前に、制限対象ホストの 403 を、サーバー自身の IP 別に集計して確認する
- 証明書の自動更新(HTTP-01)は 80 番を使う。80 番の設定を変えるときは更新を確認する

## 運用

- 本番作業のコンテナ再作成は、環境変数の既定値が効いて意図しない環境(開発モード等)で起動する事故がある。再作成の前後に、環境名の変数が本番になっているかを確認する
- 検知スクリプトの導入直後は、過去分が一斉に通知される。baseline を先に取る
- 観測期間中に他のサービスの再作成で 502 が出ることがある。集計から除く
