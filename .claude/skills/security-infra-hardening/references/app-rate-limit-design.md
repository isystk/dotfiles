# 回数制限の設計と実測

アプリ層の回数制限用。エッジ(CDN/WAF)側の制限は `references/edge-rules.md` を使う。

## 1. キーとしきい値の目安

| 対象 | 上限の例 | キー | 備考 |
|---|---|---|---|
| ログイン | 5/分 と 20/分 | メール+IP / IP | 二重。メールは小文字に正規化して数える(大文字小文字違いで迂回されない) |
| 管理画面ログイン | 5/15分 と 20/15分 | メール+IP / IP | 外周で IP 制限があっても入れる |
| パスワード再設定の要求 | 3/分 と 10/分 | メール+IP / IP | 同じ IP から異なるメールを何件でも試せる状態を塞ぐ |
| パスワード再設定の実行 | 10/分 | IP | |
| メール認証の再送 | 6/分 | ユーザー | 自分宛の送信のみでも濫用を抑える |
| 外部サービスを叩く認証情報の登録・テスト | 5/分(共有) | ユーザー | 相手側の制限を、サーバーの共有 IP で消費させない |
| 未認証の公開 API(外部 API を叩く) | 20/分 | IP | 入力は許可リスト(enum)で検証する |
| 未認証で重い GET | 60/分 | IP | 期間・件数に上限を設ける |
| 基準(全 API) | 120/分 | 認証済み=ユーザー、未ログイン=IP | 例の 60/分 より緩く始め、ログで調整する |
| Webhook(署名検証済み) | 除外 | - | 送信元のバーストを止めない |

## 2. 設計の原則

- **メール単位だけの上限(例: 30/時間)は入れない**。第三者が他人のメールで失敗を重ね、本人を締め出せる。メールは「メール+IP」の複合キーでのみ使う
- 二重に掛ける: 狭いキー(メール+IP)で総当たりを止め、広いキー(IP)で「異なるメールを順に試す」を止める
- 未認証は IP、認証済みはユーザーで数える。同じ NAT の別ユーザーを巻き込まない
- 基準の制限は「全 API に一律」+「重いものだけ個別に厳しく」。個別と基準を重ねる場合、厳しい方が先に効く
- 入力検証を先にする: 検証が通らない入力で外部 API を呼ばない。回数制限だけでは、1 リクエストあたりの増幅を防げない
- **エッジ(CDN)のレート制限と役割を分ける**: エッジは短時間の連打(10 秒に数回)、アプリは分単位の総当たり。エッジが先に効くので、アプリ側の実測はエッジの時間窓より長い間隔で行う

## 3. クライアント IP

- プロキシ配下では、信頼するプロキシを設定し、CDN のヘッダ(`CF-Connecting-IP`)から実 IP を復元する
- 復元できていないと、キーが CDN のエッジ IP になり、**利用者全員が同じ IP として数えられて誤って 429 になる**
- 確認: 別回線(スマホの回線など)から通常ログインして 429 が出ないこと。ログのクライアント IP が実 IP であること
- **IPv6 は 1 アドレス単位の制限では回避されやすい**(アドレス空間が広く、容易に切り替えられる)。同じ /64 を 1 単位にまとめて数える
  - Laravel: `by()` に渡すキーで IPv6 を /64 に丸める。Express: `ipKeyGenerator`。Django: `key` を返す関数で丸める
  - IPv6 を使わない構成なら、オリジン側で IPv6 を止めた上で、その旨を記録する(有効なまま無制限にしない)

## 4. 実測(自分が管理するサービスにだけ使う)

```bash
# 存在しないアカウントで、間隔をあけて送る(エッジの制限と区別するため 3 秒間隔)
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w '%{http_code} ' -X POST -H 'Content-Type: application/json' \
    -d '{"email":"probe@example.invalid","password":"x"}' https://your.example.com/api/login
  sleep 3
done; echo
# 待機後に通常応答へ戻るか
sleep 65; curl -s -o /dev/null -w 'after:%{http_code}\n' -X POST -H 'Content-Type: application/json' \
  -d '{"email":"probe@example.invalid","password":"x"}' https://your.example.com/api/login
```

判定基準:

- 5 回目まで 302/401/422 など通常の失敗応答で、6 回目が **429**(アプリ側のしきい値 5/分)
- 間隔なしで連打した場合は、エッジの制限(10 秒に 5 回など)が先に 429 を返す。その場合はエッジ側の確認になる
- 待機後は通常の応答に戻る
- ログインが成功する正規アカウントでは試さない(ロックの副作用を避ける)
- 実行に権限の確認が要る環境では、コマンドを利用者に渡して利用者の端末で実行してもらい、結果の数字を貼ってもらう
